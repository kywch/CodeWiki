# CodeWiki Documentation Formatting & Content Guide

This guide defines the standards for all wiki pages generated by CodeWiki. It governs both **visual formatting** (how the markdown looks) and **developer content** (what information is included). The rules below are also injected directly into the LLM prompt templates.

---

## Document Structure

Every wiki page must follow this canonical section order. Omit a section only if it truly does not apply.

```
# Module Name                          ← H1, exactly one per file
Brief 1-2 sentence purpose statement.

## Overview                             ← context, responsibilities, key concepts
## Architecture                         ← mermaid component diagram + narrative
## Core Components                      ← detailed breakdown with ### per component
## Usage & Extension                    ← entry points, config, how to extend
## Integration                          ← links to other wiki pages
```

---

## Formatting Rules

| Rule | Standard |
| :--- | :--- |
| **Headings** | Max depth `####`. Never skip levels (`##` → `####` is invalid). |
| **Unordered lists** | Always use `-`, never `*`. |
| **Ordered lists** | Use `1.` for sequential steps only. |
| **Horizontal rules** | `---` only between top-level `##` sections. Never within a section. |
| **Bold** | `**bold**` for component names on first mention in a section. Don't over-bold. |
| **Tables** | Use for structured data with ≥3 items and ≥2 attributes. |
| **Paragraphs** | 2–3 sentences max. Use bullets for lists of ≥3 items. |
| **Mermaid diagrams** | At least one per page. `graph TD` for structure, `sequenceDiagram` for flows. |

## Developer Content Requirements

### 1. Code Reference Density

Every class, function, or method name mentioned **must** be a markdown link with file path and line anchor. Zero "bare mentions" allowed.

```markdown
<!-- ✅ Good -->
The [`DependencyParser`](../codewiki/src/be/dependency_analyzer/ast_parser.py#L18) resolves symbols...

<!-- ❌ Bad -->
The DependencyParser resolves symbols...
The `DependencyParser` resolves symbols...
```

### 2. Key Entry Points

Each component description must call out the primary method with its role:

```markdown
### DocumentationGenerator
The [`DocumentationGenerator`](../path/to/file.py#L29) manages the documentation lifecycle.

- **Entry point:** [`run(repo_path, config)`](../path/to/file.py#L45) — builds the dependency graph, clusters modules, and generates all documentation. Returns the final module tree.
```

### 3. Configuration & Parameters

If the module reads from `Config` or accepts configurable parameters, include a table:

```markdown
#### Configuration

| Parameter | Type | Default | Description |
| :--- | :--- | :--- | :--- |
| `max_tokens` | `int` | `32768` | Maximum LLM response tokens |
| `use_gemini_cli` | `bool` | `False` | Use Gemini CLI instead of API |
```

### 4. Extension Points

If the module supports extension (adding a new analyzer, tool, adapter), explain the pattern briefly:

```markdown
#### Adding a New Language Analyzer
1. Create a new file in `analyzers/` implementing `__init__(file_path, content, repo_path)` and `analyze() → (List[Node], List[CallRelationship])`.
2. Register the file extension in [`CODE_EXTENSIONS`](../path/to/patterns.py#L5).
3. Add routing logic in [`CallGraphAnalyzer.analyze_code_file()`](../path/to/file.py#L30).
```

### 5. Error Handling

Document what happens on failure:

```markdown
#### Error Handling
- Raises `FileNotFoundError` if the repository path does not exist.
- Catches `tree_sitter` parse errors and logs a warning, skipping the file.
- Returns an empty `AnalysisResult` if no supported files are found.
```

### 6. "Start Here" Callout

Begin the Core Components section by indicating where a developer should start reading:

```markdown
## Core Components

> **Start here:** [`DocumentationGenerator`](../path/to/file.py#L29) is the main entry point. Read its `run()` method first.
```

## Example: Well-Formatted Component Section

```markdown
### AgentOrchestrator

The [`AgentOrchestrator`](../codewiki/src/be/agent_orchestrator.py#L62) manages the lifecycle of individual AI agents, determining module complexity and configuring agents accordingly.

- **Entry point:** [`process_module(module_name, components, module_tree)`](../codewiki/src/be/agent_orchestrator.py#L85) — prepares the environment and runs the agent to generate a `.md` file. Returns the updated module tree.
- [`create_agent(is_leaf)`](../codewiki/src/be/agent_orchestrator.py#L70) — instantiates a `pydantic_ai.Agent` with different system prompts and toolsets depending on module type.

#### Configuration

| Parameter | Type | Default | Description |
| :--- | :--- | :--- | :--- |
| `use_gemini_cli` | `bool` | `False` | Skip iterative agent loop; use single-call generation |
| `max_tokens` | `int` | `32768` | Response token limit for the agent |

#### Error Handling
- Catches LLM timeout errors and retries once with a longer timeout.
- Logs and skips modules that fail after retry.
```
